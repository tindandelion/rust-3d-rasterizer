## 1. Which line algorithm is in the codebase?

- **`FrameBuffer::draw_line`** in **`src/framebuffer.rs`** is **DDA-style**, not integer Bresenham.
- **Mechanics:** integer **`steps = max(|Δx|, |Δy|)`**; loop **`i = 0..=steps`** with **`t = i/steps`** (or **`t = 0`** if **`steps == 0`**); **`f64`** endpoint interpolation **`(x0 + dx·t, y0 + dy·t)`**; **`.round()`**; **`set_pixel`** (guard-skips OOB); doc comment labels it **DDA-style**.
- **Alignment:** **`doc/planning/project-spec.md`** calls for **DDA-style** stepping with float increments acceptable.
- **Historical note:** an older session diary (**`session-2026-05-10T18-00-00.md`**) records **Bresenham** for diagonals early on, then a deliberate **rewrite to DDA** to match the plan.

## 2. Bresenham — conceptual summary (session explanation)

- **Goal:** choose next pixel on a grid so the staircase tracks an ideal segment, using an **integer decision variable** (error / midpoint test), avoiding per-pixel floating work.
- **First-octant picture:** step **one pixel along the dominant axis** each iteration; **binary choice** on the other axis (`y` stays or increments). General case: **swap/mirror** so the same kernel applies.
- **Contrast with DDA:** DDA is closer to “pure math” (**parameter `t`**, interpolate, round); Bresenham is the classic **integer-ops** inner loop.

## 3. Worked example: `(0,0)` → `(5,2)`

- **Setup:** **`dx = 5`**, **`dy = 2`**, start **`D = 2*dy - dx = -1`**. After drawing **`(0,0)`**, loop **`dx`** times: update **`D`** (either **`D += 2*dy`** or **`D += 2*dy - 2*dx`** and **`y++`**), then **`x++`**, draw.
- **Pixel order:** **`(0,0) → (1,0) → (2,1) → (3,1) → (4,2) → (5,2)`**.
- **Sanity:** ideal line **`y = (2/5)*x`** at **`x = 1..4`** gives **`0.4, 0.8, 1.2, 1.6`**; staircase rows match the usual nearest-pixel pattern for this formulation.

## 5. Decision: keep DDA for now

- **Rationale:** DDA is **easier to reason about** (closer to analytic geometry); for this **learning / CPU rasterizer** scope, **`draw_line`** is **unlikely** to dominate cost versus the rest of the pipeline.
- **Future:** consider **Bresenham** (or variants) **only if profiling** shows line rasterization is a real bottleneck.

## 6. Antialiasing — directions surveyed (deferred)

Discussion only; **no implementation** in this session.

- **Lines / wireframe:** **Wu (Xiaolin Wu)**; **distance- or coverage-based** thick line / band; **supersampling (SSAA)** then downsample (simple, costly).
- **Filled triangles (later):** **subpixel / analytic coverage**; extend **half-space / scanline** with partial coverage; **post-process** (e.g. FXAA — fast but not geometrically faithful).
- **Whole frame (later still):** **temporal AA** — plausible on GPU paths first; more moving pieces on CPU.

**User closure:** **leave antialiasing for later**; reopen when wireframe vs fills priorities are clearer.
